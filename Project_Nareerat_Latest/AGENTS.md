# AGENTS.md — guide for AI coding agents

Read this before changing anything. `README.md` is the original Thai user manual and is out of date
(it describes the old FAQ-based system); this file describes the code as it is.

## What the system is

A localhost RAG web app that answers questions about the Thai insurance regulator's (OIC / คปภ.)
**IBS-Life data-submission spec**: which field to send, its meaning, type, submission rules, known problems and fixes.

- Knowledge base (two sources, **no FAQ.xlsx** — it was removed as a source):
  1. `data/Fields_4.0.csv` → 300 fields in 23 tables (Policy, Payment, Claim, Estimate, SIMB2 …).
  2. `data/IBSL-PR-INC_001_V1.0_25690813(1).pdf` (Incident & Problem Analysis, 133 pages) → 45 topics (1.1.1–1.11.3)
     with problem / rules / examples / guidance / structured example tables / payload.
- **Scope: policy data only (the user's requirement).** The engine loads the Policy table and its 13 descendant
  tables (**209 fields in 14 tables**: Customer, Insured, InsuredBeneficiary, SubPolicy, PolicyCovPlanSeq,
  CoveragePlanCoverage, Coverage, Beneficiary, Endorsement, Loan, LoanPayment, Investment, PolicyFundCode) and the
  **24 IBSL topics of categories 1.1–1.6** (PDF pages 6–74). Payment, Claim, Estimate, Claim Payment, SIMB2 and IBSL
  1.7–1.11 are left out. The scope is applied only in `rag_engine.py` (`POLICY_ROOT_TABLE`, `POLICY_IBSL_CATEGORIES`);
  `data_rag/` stays a complete conversion of the sources. `IBSL_SCOPE=all` loads everything (tests assume `policy`).
- Stack: Python FastAPI backend, single-page frontend (plain JS + Tailwind CDN + Lucide icons), SQLite, no Node build.
- UI and all user-facing text are **Thai**. Keep new user-facing text in Thai.
- Not a git repository. There is no version control: back up files before large edits.

## Run / test

```bash
pip install -r requirements.txt
python run_server.py                        # http://127.0.0.1:8000 (PORT in .env)
python -m unittest discover -s tests -v     # unit tests (14), use a temp SQLite DB, safe to run
python scripts/build_rag_dataset.py         # rebuild data_rag/fields.json, tables.json, glossary.json, corpus.jsonl from Fields_4.0.csv
python scripts/build_ibsl_dataset.py        # rebuild data_rag/ibsl_* from the IBSL-PR-INC PDF; prints + writes data_rag/IBSL_REPORT.md (all checks must PASS); needs pip install pypdf pdfplumber pypdfium2
python scripts/export_feedback_to_ground_truth.py [--merge]   # writes data/ground_truth*.json (old FAQ-era format; the engine does NOT read it)
```

`tests/test_live_server.py` hits a running server on port 8000 and writes searches to that server's DB.
To test against a throwaway server: start uvicorn on another port with `IBSL_DB_PATH=<temp file>`.
Set `IBSL_EMBEDDING=local` for deterministic retrieval checks (Gemini embeddings otherwise, when a key works).

Windows note: `curl` in Git Bash mangles Thai JSON bodies (searches silently return 0 results).
Use Python `urllib` with explicit UTF-8 for API tests. Set `PYTHONIOENCODING=utf-8` when printing Thai.

## Data pipeline

1. `data/Fields_4.0.csv` → `scripts/build_rag_dataset.py` → `fields.json`, `tables.json`, `glossary.json`, `corpus.jsonl`,
   `DATA_REPORT.md`. Cleans Thai text, adds aliases/keywords (hand-written `TABLE_META`, `GLOSSARY`, `FIELD_ALIASES`),
   fixes broken descriptions (`DESC_FIXES`). Regenerating reproduces the current data exactly.
2. The PDF → `scripts/build_ibsl_dataset.py` → `ibsl_items.json` (45 topics; sections problem / conditions /
   invalid_examples / valid_examples / guidance / validation_table (text) / payload; plus `validation_tables`
   (structured rows, `key_fields`, `tested_fields`, `test_cases`), `validation_table_md`, `question_code_note`),
   `ibsl_chunks.jsonl`, `ibsl_pages.json` (+ `doc_info`), `ibsl_document.md`, `IBSL_REPORT.md`.
   The PDF itself repeats some question codes and prints wrong field names in 5 tables: kept as printed, listed in
   `IBSL_REPORT.md`. Use `item_id` (`IBSL-1.2.1`), not the question code, as the key.
3. The index cache stores a `data_signature()` (file mtimes/sizes of fields/tables/ibsl_items/ibsl_chunks/ibsl_pages).
   A mismatch triggers a rebuild automatically on startup; `POST /api/reindex` forces one.

IDs: fields are `FIELD-<field_name>` (shared by search results, SQLite and ground truth); IBSL topics are `IBSL-<section_no>`.

## Search pipeline (`/api/search`)

1. `retrieve(query)`: every field record is scored = cosine × 4 (TF-IDF word+char, or Gemini) + lexical bonuses:
   exact field name; **name evidence = the strongest of** description match (exact `DESC_EXACT_BONUS`, substring —
   scaled down when the query is inside many descriptions —, or most query words in the description), sub-table
   for container fields, field alias (weak when a short alias sits inside a long query); table name/alias;
   **table queries**: when the query equals a table name/alias, or sits in the descriptions of >= 60% of hits and
   >= 50% of one table's fields (`_query_context`), the container field gets `TABLE_NAME_BONUS` and every field
   of that table `TABLE_MEMBER_BONUS` ("ผู้เอาประกันภัย" -> insureds + insrd_*);
   IBSL question code (abbreviations like POL_001 match) / section number / error code.
   The description-share rule also needs the query to be >= 60% of the table's name/entity/alias
   (`TABLE_QUERY_MIN_NAME_COVERAGE`), so "เบี้ยประกัน" is not taken as the Customer table ("ผู้ชำระเบี้ยประกันภัย").
   Keep results ≥ 35% of the top score (no count cap, `DEFAULT_MAX_RESULTS = None`), plus — UI only (k=None) — fields whose name matches/resembles a field named in the query (`NAME_MATCH_REASONS`), so "pol_status" also returns pol_status_date / pol_status_note. The frontend sends no `top_k`, so the UI shows
   every result that passes the cutoff (do not put `top_k: 3` back). Tests 13–14 guard that every field is found by
   its name and its exact Thai description.
2. Each field record carries its IBSL topics (`ibsl_topics`): the topic whose `field_names` contain the field comes
   first and becomes `primary_ibsl`; topics that only mention it follow. Topic fields that Fields_4.0 lacks
   (`claim_icd_9_codes`) get an IBSL-only record (`ibsl_only: true`) so the topic is still retrievable.
3. The index text of a field includes the titles/codes of all its topics, but topic content (problem, rules,
   guidance, error codes, examples, test cases) only from the topic it is the subject of — otherwise pol_id
   (mentioned in nearly every payload) was drowned and "เลขที่กรมธรรม์" did not find it.
4. `apply_user_feedback`: net < 0 → hidden; net > 0 → moved to top (re-added if cut off).
5. Answer: evidence per field (spec + up to 2 topics incl. structured test cases and payload) → Gemini or OpenAI;
   deterministic Thai fallback when no key.
6. External "AI Agent" advice is per field card, not part of `/api/search`: the frontend calls `/api/external`
   for each card (the first `EXTERNAL_AUTO_LOAD` = 3 automatically, others/retries via a button). Tavily search on
   query + field name + description; successful results cached in memory (`EXTERNAL_CACHE_MAX`).

All tunables are module constants at the top of `rag_engine.py`. Change them there, not inline.

## Evaluation — two separate things

- **Ground Truth benchmark** (`evaluate_ground_truth`, `data_rag/ground_truth_ibsl.json`, 12 cases; cases expecting
  fields outside the scope are skipped and listed in `skipped_out_of_scope` → 7 policy cases):
  `retrieve(q, k=3, rel_threshold=0.60)`, macro P/R/F1@3. **Deliberately ignores user feedback** — do not wire
  feedback into it. Policy scope, `IBSL_EMBEDDING=local`: P 0.810 / R 0.643 / F1 0.701.
- **User evaluation** (`get_user_precision_metrics`): P@3 over ranks 1–3 only, counted only when all
  top-3 items were rated. No recall/F1 from user clicks (the full relevant set is unknown).

## API

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/status` | counts (pages, topics, fields), LLM/web-search configuration |
| POST | `/api/search` | `{query, top_k?}` → `items` (field records with IBSL detail), answer, `feedback_applied`, `query_id` |
| POST | `/api/external` | `{query, item_id}` → AI Agent advice for one field: status, message, sources, cached |
| POST | `/api/evaluate` | `{query_id, evaluations:[{item_id, relevance 0/1}], comment?}` |
| DELETE | `/api/evaluate/{query_id}` / `/api/evaluate` | delete one / ALL evaluations (no auth!) |
| GET | `/api/metrics` | `user_evaluation` + `ground_truth` |
| GET | `/api/fields` | field catalog for the รายการฟิลด์ข้อมูล tab |
| POST | `/api/reindex` | rebuild the index |

## Rules for agents

- **Never modify `data/` source files.** Change the build scripts and regenerate `data_rag/`.
- **Never write test data into `storage/database.sqlite`** — it holds real user evaluations. Use `IBSL_DB_PATH`.
- **Never print, copy or commit API keys.** `.env` and (currently) `.env.example` contain real-looking keys that should be revoked.
- Don't tune scoring against the ground-truth cases alone; it overfits. Check a broader query set
  (e.g. ทุนประกัน, เบี้ยประกัน, คืนเงินกู้, วันเกิด, pol_id, sub_pol_start_date, xyzabc12345 → must return nothing).
- The user asked for no version numbers ("4.0") and no field counts in UI text. Keep counts dynamic (`/api/status`, `/api/fields`).
- Tests encode the requirements (topic counts, cut-off behaviour, feedback, metrics). Update tests together with intentional behaviour changes.
- After editing `frontend/app.js`, run `node --check frontend/app.js`. A syntax error there disables every button in the UI.

## Known limitations (not yet solved)

- Ground truth has only 7 in-scope cases → scores are noisy.
- A query naming an out-of-scope field (e.g. claim_hospital_id) still returns look-alike policy fields
  (pol_claim_url, cov_claim_status …); there is no explicit "outside the policy scope" message yet.
- Aliases and description fixes in `data_rag/` were written without an IBSL expert; see `data_rag/DATA_REPORT.md`.
- Retrieval is over field records only; a question that names no field and matches no alias may miss its topic.
- The frontend shows `validation_table` as plain text; the structured `validation_tables` is not rendered as a table yet.
- Feedback applies only to the identical query text; one rating changes results for everyone.
- No auth: anyone reaching the server can delete all evaluations.
- LLM answers are not checked against the retrieved evidence.
